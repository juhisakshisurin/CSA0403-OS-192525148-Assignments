## Objective

To evaluate CPU execution modes, privileged instructions, interrupts and memory-protection mechanisms in the context of a smart hospital.

## 1. Introduction

CPU protection mechanisms prevent user programs from performing unauthorised operations and protect operating-system resources.

In a smart hospital, bedside monitoring applications must process sensor readings within the required response time. At the same time, applications must be isolated from sensitive patient data and critical operating-system functions.

## 2. User Mode and Kernel Mode

| Feature | User Mode | Kernel Mode |
|:---|:---|:---|
| Execution | Runs application programs. | Runs operating-system kernel code. |
| Privileges | Restricted access. | Full privileged access. |
| Hardware Access | Cannot directly execute privileged hardware operations. | Can execute privileged instructions. |
| Memory Access | Restricted to permitted address spaces. | Can access protected kernel memory. |
| Examples | Medical application, browser and user programs. | Device drivers, memory management and process scheduling. |

The CPU uses a mode bit to distinguish between user mode and kernel mode.

## 3. Privileged Instructions

Privileged instructions are operations that can only be executed in kernel mode.

Examples include:

- Controlling hardware devices.
- Modifying memory-management registers.
- Disabling or enabling interrupts.
- Changing CPU control settings.

If a user program attempts to execute a privileged instruction, the hardware generates a protection exception.

## 4. Interrupts and Traps

An interrupt is a signal that requires the CPU's attention. It may be generated by a hardware device.

A trap is a controlled transfer of execution to the operating system, often caused by a system call or an exception.

### Importance in the Smart Hospital

A bedside monitor may receive abnormal sensor readings. Interrupt-driven handling allows the system to respond to device events without continuously checking the device.

A timer interrupt also allows the operating system to regain CPU control and schedule other processes.

## 5. CPU Protection and Memory Protection

CPU protection is maintained using hardware-supported mechanisms.

### Memory Management Unit (MMU)

The MMU checks memory accesses and ensures that a process accesses only permitted memory locations.

### Page Tables

Each process has its own virtual-memory mappings. Page-table permissions control whether memory can be read, written or executed.

### Memory Protection Fault

If a program attempts to access memory without permission, the hardware generates an exception. The operating system handles the exception and may terminate the program.

### Process Isolation

Each process operates in its own protected address space. This prevents one application from directly reading or modifying another application's private memory.

In the hospital system, this prevents an ordinary application from directly accessing sensitive patient records stored in another process's memory.

## 6. Alternative Concept and Complexity Analysis

**Alternative:** Polling Instead of Interrupts.

In an interrupt-driven system, the CPU responds when a sensor generates an interrupt.

In a polling-based system, the CPU continuously checks the sensor at regular intervals to determine whether an abnormal reading has occurred.

### Comparison

| Feature | Polling | Interrupt-Driven I/O |
|:---|:---|:---|
| CPU Activity | Repeatedly checks the device. | Responds when an event occurs. |
| CPU Usage | Can waste CPU time while waiting. | Allows CPU to perform other work. |
| Response | Depends on polling interval. | Depends on interrupt latency and processing time. |
| Suitable Use | Fixed-interval sensor checking. | Event-driven monitoring. |

### Worst-Case Delay Calculation

Assume the sensor is checked every 5 milliseconds.

`Polling interval = 5 ms`

Worst-case detection delay:

`Worst-case delay = Polling interval = 5 ms`

For an interrupt-driven system:

`Response delay = Interrupt latency + Processing time`

If interrupt latency is 0.5 ms, the event can begin processing much earlier than waiting for the next 5 ms polling cycle.

These are illustrative values, not measured hospital-device results.

### Time Complexity

Let `n` represent the number of sensor checks.

- Polling: `O(n)`, because the CPU repeatedly checks the sensor.
- Interrupt handling: `O(k)`, where `k` represents the number of interrupt events handled.

### Space Complexity

- Polling: `O(1)` additional space for a simple sensor-checking loop.
- Interrupts: `O(1)` additional space for a simple interrupt handler, excluding operating-system and hardware data structures.

### Evaluation

Polling is suitable when sensor checks are required at fixed intervals and the interval is sufficiently small.

However, interrupt-driven I/O is generally more efficient for hospital monitoring because the CPU can respond to sensor events without continuously checking for them.

For bedside patient monitors, an interrupt-driven approach is recommended, provided its worst-case response time is measured and verified to satisfy the 10 ms deadline.

## 7. Conclusion

CPU protection mechanisms are essential for maintaining the security and reliability of a smart hospital.

User mode and kernel mode prevent unauthorised operations, interrupts allow quick responses to hardware events, and memory protection prevents processes from accessing one another's private memory.

An interrupt-driven approach is recommended for bedside monitoring because it supports efficient event handling and helps meet the required 10 ms alarm deadline.
